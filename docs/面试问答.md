# mini-agent 面试问答（12 题）

> 投递前把这份读完，能用自己的话讲出来再写进简历。任何一题答不上来，就把对应实现重读一遍。

## 1. 这个项目解决什么问题？

把 Agent 的运行时拆开：模型只负责"决定下一步做什么"，剩下的调度、参数校验、错误兜底、状态记录都由我写的那一层负责。所以它不是"调 API 的脚本"，而是一个能复现、能测试的最小运行时。

## 2. 一次工具调用怎么流动的？

`Agent.run(task)` → 把消息历史 + 工具清单交给 `llm.plan()` → 后端返回 `{"tool":..., "args":...}` → `ToolRegistry.call()` 校验参数 → 调工具函数 → 结果变成一条 `role=tool` 的消息追加进历史 → 下一轮 `plan()` 基于它继续。最后模型返回 `{"final": ...}` 时结束。

## 3. 工具是怎么"注册"的？

`Tool` 数据类 = 名字 + 描述 + JSON Schema + 函数。`ToolRegistry.register()` 拒绝重名，`.call()` 用 schema 校验必填项、类型、未知参数，通过后才调函数。这样模型幻觉出一个不存在的参数名时，得到的是可读的错误而不是 Python 报错栈。

## 4. 参数校验都校验了什么？

三件事：必填项缺失、类型不符（`integer` 不接受 bool，这是 Python 的坑）、出现 schema 里没有的字段。都抛 `ToolError`，由循环捕获成 observation。

## 5. 工具执行失败会怎样？

`ToolError` 被循环捕获，转成 `ERROR: ...` 的观察继续下一轮，最多到 `max_steps`。测试 `test_tool_error_becomes_an_observation` 覆盖了这条路径：故意少传参数，跑满步数后返回 "step limit"，且第 1 步被记为 `error`。

## 6. 怎么防止 Agent 死循环？

`max_steps` 默认 6；到达上界时返回明确的文案而不是抛异常。测试 `test_max_steps_bounds_the_run` 用一个"永远只想调工具"的假后端验证：跑满 3 步就停。

## 7. 为什么要有 Mock 后端？不是多此一举吗？

测试不能依赖网络和 key。Mock 是确定性的规则规划器（识别算术、时间、记笔记、SQL 四种意图），和真实后端实现同一个 `plan()` 接口，于是循环逻辑、校验、trace、记忆全部可以离线跑，CI 也稳定。

## 8. 真实后端怎么接的？

任何 OpenAI 兼容的 `/chat/completions`：请求里带 `tools`（把每个工具的 schema 转成 function 定义）和 `tool_choice: auto`，从响应的 `message.tool_calls[0].function` 里取名字和 JSON 参数。所以 DeepSeek、Moonshot、本地 vLLM 都能用，改 `DEEPSEEK_BASE_URL` 就行。

## 9. 会话记忆怎么做的？

整段 messages 存成 JSON，`--session name` 指定文件，下一轮启动时加载，所以能接着上次对话。局限是没做压缩和检索，长会话会越来越大。

## 10. trace 里记了什么？为什么需要？

每步一条 JSONL：步号、类型（tool/error/final）、工具名、参数、观察、时间戳。作用是复现一次失败的运行——用户说"它答错了"，看 trace 就知道是模型选错了工具，还是工具返回了空，还是参数没通过校验。

## 11. 计算工具为什么要自己写表达式校验？

直接用 `eval` 会被注入（比如 `__import__('os').system(...)`）。我的做法：正则白名单只放数字和 `+ - * / ( ) . %`，再用 `compile(..., 'eval')` 配合空的 `__builtins__` 执行，除零单独捕获成可读错误。

## 12. 这个项目最大的不足是什么？

三个：没有多工具并行/嵌套调用；没有真正的沙箱（工具函数拿到的是整个进程的权限，`sqlite_query` 只能靠只读连接自己约束）；记忆没有压缩。下一步会先做"工具调用的超时与重试"，因为这是生产环境最先暴露的问题。
